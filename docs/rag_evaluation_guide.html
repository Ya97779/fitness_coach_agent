■ 四大评测指标

RAGAS 框架从检索质量和生成质量两个维度评估 RAG 系统，共 4 个指标：

忠实度
Faithfulness
回答是否忠于检索到的上下文，衡量幻觉程度。将回答拆分为独立声明，逐一验证是否能从 contexts 中推导。
= |supported claims| / |total claims|
回答相关性
Answer Relevancy
回答与原始问题的相关程度。用 LLM 从回答反推可能的问题，计算生成问题与原始问题的余弦相似度。
= mean(cos_sim(q_gen, q_orig))
上下文精确度
Context Precision
检索结果的排序质量。相关文档是否排在前面？采用加权精度公式，排名靠前的相关文档得分更高。
= Σ(precision@k × rel_k) / |relevant|
上下文召回率
Context Recall
ground_truth 中的正确信息被检索到的比例。将标准答案拆分为声明，逐一检查是否出现在 contexts 中。
= |recovered claims| / |gt claims|

◆ 模块架构

ModernRAG — 主入口

backend/app/rag/__init__.py

统一检索入口，支持 5 种检索模式，内部管理所有子模块的初始化和生命周期。

  • search(query, mode) — 检索接口，返回 List[Dict]，每个结果含 content + score + metadata
  • query(query) — 检索 + 生成，返回 answer + contexts
  • LRU 缓存 — 128 条，5 分钟 TTL，key = {query}|{top_k}|{mode}
  • 增量索引 — 启动时扫描 knowledge_base/，MD5 对比，新增/更新/删除
# 5 种检索模式 mode = "hybrid" # 向量 + BM25，RRF 融合（默认） mode = "vector" # 仅 Chroma 向量检索 mode = "bm25" # 仅 BM25 关键词检索 mode = "query_expansion" # 多查询扩展 mode = "hyde" # 假设性文档嵌入

HybridSearch — 混合检索

backend/app/rag/modules/hybrid_search.py

通过 Reciprocal Rank Fusion (RRF) 融合向量检索和 BM25 检索结果。

  • 向量检索和 BM25 各取 top_k × 2 候选
  • 通过精确内容匹配（page_content 字符串比对）关联两个结果集
  • RRF 公式：score = weight × 1/(k + rank)，k 默认 60
  • 最终按融合分排序（Chroma 使用 L2 距离，越小越好）

BM25Search — 关键词检索

backend/app/rag/modules/bm25.py

从零实现的 BM25 算法，使用 jieba 中文分词。

  • 分词：jieba.lcut() + 小写归一化
  • TF 饱和：tf × (k1+1) / (tf + k1×(1-b+b×dl/avgdl))，k1=1.5, b=0.75
  • IDF：log((N-df+0.5)/(df+0.5) + 1)
  • 无停用词过滤，无标点清洗，无最小 token 长度过滤

HyDE — 假设性文档嵌入

backend/app/rag/modules/hyde.py

用 LLM 生成一个「假设性答案」，再用这个答案去向量检索，缩小查询与文档的语义差距。

  • LLM 生成 100-300 字的假设文档（temperature=0.8）
  • 分别用假设文档和原始查询做向量检索
  • 分数合并：0.5 × hyde_score + 0.5 × original_score
  • retrieve_with_alternatives 参数 num_alternatives 实际未生效

Self-RAG — 自我反思

backend/app/rag/modules/self_rag.py

通过 LLM 自我评估实现检索-生成-反思-纠正的闭环。

  • should_retrieve — LLM 判断是否需要检索
  • score_relevance — 对每个检索片段打分 0-4，过滤低于 2.0 的
  • score_utility — 对生成的回答打分 0-4，低于 2.5 触发纠正
  • correct_answer — 纠正循环最多 2 次
  • 每次查询最少 3 次 LLM 调用，纠正时可达 7+ 次

Agentic RAG — 智能路由

backend/app/rag/modules/agentic_rag.py

LLM 自主决策检索策略和生成策略。

  • RouterAgent — 分析查询，输出 JSON 决策（检索策略 + 生成策略 + 优先级）
  • 检索策略：no_retrieval / basic / hyde / query_expansion / cot / self_rag
  • 生成策略：direct / rag_based / cot / self_reflect
  • QueryClassifier 已定义但从未被调用（死代码）
  • cot 和 self_rag 策略实际都走 hybrid 检索，仅生成阶段不同

严重度 模块 缺陷描述 影响
高 __init__.py BM25-only 模式每次调用都重建索引：BM25Search() + index() 在每次 search(mode="bm25") 时重新执行 严重性能浪费，hybrid 路径已有 BM25 索引却未复用
高 self_rag.py 评分解析脆弱：score_relevance 和 score_utility 依赖 LLM 输出格式（中文关键词 + 数字），格式不符则默认 2 分 评分静默失败，导致低质量内容被保留或高质量内容被过滤
中 hybrid_search.py 向量/BM25 结果关联依赖精确字符串匹配（page_content 比对），格式微差即匹配失败 静默退化为单路检索，RRF 融合失效
中 bm25.py 无停用词过滤、无标点清洗、无最小 token 长度过滤，jieba 单字 token 全部保留 BM25 检索精度下降，噪声 token 干扰 TF/IDF 计算
中 agentic_rag.py cot 和 self_rag 检索策略实际都调用 search(mode="hybrid")，与 basic 策略完全相同 路由决策形同虚设，检索阶段无差异化
中 agentic_rag.py QueryClassifier 已定义但 RouterAgent.decide() 从未调用其 classify() 方法 死代码，浪费初始化开销
中 self_rag.py 纠正循环无收敛检查：即使纠正后分数未提升，仍会继续消耗 LLM 调用 浪费 token，最多白跑 2 次纠正
中 __init__.py force_rebuild 参数被构造函数接受但从未传递给 _init_components() 死代码，无法通过参数强制重建索引
中 test_rag_evaluation.py 使用 RAGAS 私有 API（_Faithfulness、_AnswerRelevancy 等下划线前缀） RAGAS 版本升级后可能直接报错
中 eval_dataset.json 仅 15 条测试用例，RAGAS 官方建议 50+ 条 评估结果缺乏统计显著性
低 hyde.py retrieve_with_alternatives 的 num_alternatives 参数被忽略，实际只生成 1 个 功能名与实现不符
低 agentic_rag.py 置信度估算使用硬编码增量（+0.2/+0.1/-0.1），无证据支撑 置信度数值无实际参考价值
低 test_rag_evaluation.py NaN 过滤使用 v == v 技巧而非 math.isnan() 可读性差，功能正确
低 test_rag_evaluation.py fallback 链每次触发都新建 ChatOpenAI 实例 资源浪费，但 fallback 触发频率低
低 eval_dataset.json expected_topics 字段在评测代码中从未使用 死数据，可扩展为自定义 topic-coverage 指标
