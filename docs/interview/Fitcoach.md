## Q2：为什么要做这个项目？用户真正的问题是什么？

### 推荐回答

我观察到健身领域并不缺内容，真正缺少的是“把信息转化为当前用户下一步行动”的能力。

用户通常面临三个问题：

- 信息碎片化：动作教学、饮食热量和训练建议来自不同渠道，口径不一致。
- 建议缺少个性化：通用答案不知道用户的体重、目标、伤病、过敏和当天状态。
- 数据没有闭环：用户记录了饮食和运动，但系统没有把记录转化成持续反馈。

所以我没有把产品定位成另一个百科问答，而是希望形成这样的闭环：

```text
理解用户意图
→ 读取用户状态
→ 查询知识或调用业务工具
→ 写入真实数据
→ 回读结果
→ 基于长期变化继续建议
```

RAG 解决“建议有什么专业依据”，工具解决“系统能不能真正执行”，记忆解决“下一次是否还理解这个用户”。

### 产品层面的核心取舍

不是所有场景都应该交给 Agent。登录、精确查询、记录和删除等确定性任务应由业务服务处理；只有模糊、跨领域、需要上下文推理或工具选择的任务才需要模型参与。

## Q3：为什么后来要进行架构升级？原架构有什么问题？

### 推荐回答

升级不是为了追求更新的框架，而是线上体验和维护过程暴露出了原架构的边界。

主要有六类问题：

1. **路由过于机械**：根据关键词计数在 chat、nutrition、fitness 中三选一。“记录一下跑步”可能因为“记录一下”被分到营养，“第二个呢”因为没有领域词被分到闲聊。
2. **上下文不是真正的会话状态**：接口没有稳定的 `session_id`，历史文本被拼入 System Prompt，既容易重复，也存在持久化提示词注入风险。
3. **流式体验名不副实**：部分路径会先等待完整模型调用或收集完整回复，再逐段输出，用户看到的是“长时间等待后快速打字”。
4. **工具边界不安全**：模型工具参数中包含 `user_id`，理论上模型可能生成不属于当前用户的 ID。
5. **数据一致性不足**：客户端超时重试可能重复写入；同一用户同一天可能并发创建多条日志；食物缓存只按名称判断，无法区分每 100g、每 100ml 和每个。
6. **缺少可观测性**：只能知道“回答很慢”，无法判断是鉴权、数据库、路由、模型排队、模型首块还是 Nginx 缓冲造成的。

因此升级目标不是增加更多 Agent，而是先让现有 Agent 具备可靠的身份、状态、路由、执行和观测基础。

## Q4：维护前后，整体架构发生了什么变化？

### 维护前

```text
用户消息
→ 关键词计数
→ chat / nutrition / fitness 三选一
→ 单轮 Prompt + 历史文本拼接
→ 模型或工具调用
→ 收集结果
→ 返回并保存一条 ConversationLog
```

### 维护后

```text
微信小程序
→ FastAPI JWT 鉴权
→ RequestContext(user_id, session_id, request_id)
→ 立即发送 SSE 状态
→ MemoryManager 构建受预算约束的上下文
→ 结构化 RouteDecision
   ├─ 明确记录：确定性快速路径
   ├─ 短追问：承接会话工作记忆
   └─ 模糊问题：LLM 结构化路由
→ chat / nutrition / fitness 能力与工具
→ reasoning/content 真流式输出
→ 成功后保存情景记忆、路由状态和幂等游标
```

### 核心变化对比

| 维度 | 维护前 | 维护后 |
| --- | --- | --- |
| 路由 | 关键词分数和固定优先级 | 规则、上下文、结构化 LLM 组合决策 |
| 路由结果 | 一个 Agent 名称 | mode、domain、intent、tools、safety、confidence、reason_code |
| 用户身份 | 可能信任工具参数 | JWT 后端绑定，工具不能自行选择用户 |
| 会话 | `session_id` 不稳定 | 客户端持久化 `session_id`，服务端保存会话状态 |
| 记忆 | 画像、统计、历史字符串 | 工作、情景、语义三层记忆 |
| 上下文 | 原始历史拼入 System Prompt | 规范的 Human/AI 消息 + 字符预算 |
| 流式 | 部分路径先生成后输出 | 模型块到达后立即通过 SSE 向上游传递 |
| 并发 | 流式信号量提前释放，工具绑定可绕过 | 统一 LLM 代理覆盖完整流和工具绑定 |
| 写操作 | 重试可能重复执行 | `request_id` 回放 + 数据库唯一约束 |
| 前端 | 按数组位置更新消息 | 按稳定消息 ID 更新当前回复 |
| 配置 | 行为开关与密钥混在 `.env` | `config.yaml` 管行为，dotenv 主要保存密钥 |
| 运维 | 修改后难以判断是否真正生效 | 固定部署分支、迁移脚本、systemd 与请求时序日志 |

### 面试总结句

> 维护前是“根据一句话选择一个角色”；维护后是“在受控请求上下文中，根据会话状态选择规则、模型或工具，并对执行结果负责”。

## Q5：现在它是一个真正的 Agent，还是仍然是 Workflow？

### 推荐回答

我会把当前系统定义为“混合式 Agent 架构”，而不是完全自治 Agent。

它已经具备一部分 Agent 特征：

- 能基于当前消息和会话状态做结构化决策；
- 能选择专业能力和工具；
- 能读取用户记忆和业务状态；
- 能执行写操作并保存结果；
- 遇到低置信度、安全信号或多领域问题时采用不同策略。

但它还没有完整实现通用的“规划—执行—观察—反思—恢复”循环。例如跨领域建议目前主要由主教练 Prompt 统一回答，只有明确的饮食加运动记录会真正拆成两个写操作；训练计划版本化、任务暂停恢复和器械照片识别仍是后续阶段。

我认为这是合理的演进顺序。涉及真实用户数据时，先用规则和业务服务保证安全与确定性，再逐步扩大模型自治范围，比一开始就构建复杂自主循环更可靠。

## Q6：你是如何改造 Agent 路由的？

### 原方案的问题

原方案按关键词累计分数，出现以下典型误判：

- “你今年多少岁”因为“多少”进入营养 Agent；
- “记录一下跑步 30 分钟”可能因为“记录一下”进入营养 Agent；
- “增肌期间训练和饮食怎么安排”只能三选一；
- “第二个呢”“换成哑铃”无法承接上一轮。

### 当前方案

当前仍复用原来的 `hybrid_route()` 入口，但返回结构化 `RouteDecision`：

```json
{
  "agent": "fitness",
  "mode": "fast_action",
  "primary_domain": "fitness",
  "domains": ["fitness"],
  "intent": "record",
  "needs_tools": true,
  "needs_clarification": false,
  "safety_flags": [],
  "confidence": 0.94,
  "reason_code": "EXPLICIT_EXERCISE",
  "method": "rule"
}
```

决策顺序是：

1. 高精度规则识别明确饮食记录、运动记录、查询和安全信号。
2. 对“第二个”“继续”“换成”等省略句，读取上一轮路由和近期消息。
3. 只有规则不确定时才调用 LLM，并要求返回严格 JSON。
4. 结构化结果经过枚举、置信度和字段校验，解析失败则安全降级。

### 为什么不是所有请求都调用 LLM 路由？

因为明确记录任务的目标是低延迟和不误写。模型路由会增加一次网络调用，也可能输出格式错误。将高确定性请求留给规则，把 LLM 用在模糊语义上，是准确率、成本和延迟之间更合适的平衡。

### 当前限制

路由已经能识别 `multi_domain`，但除明确双记录外，通用跨领域任务还没有完整的子任务调度器；当前由 chat 主入口以主教练视角综合回答。

## Q7：三层记忆架构是怎么设计的？

### 当前实现

| 层级 | 数据载体 | 保存内容 | 生命周期 |
| --- | --- | --- | --- |
| 工作记忆 | `ConversationSession` | 当前 Agent、上一轮路由、待办状态、最后请求 ID、最近结果 | 会话级 |
| 情景记忆 | `ConversationLog` | 每一轮真实发生的用户问题和成功回答 | 按时间保留 |
| 语义记忆 | `UserMemory` | 目标、偏好、伤病、过敏等可复用事实 | 长期，可确认、过期和删除 |

### 为什么业务数据不直接放进记忆？

`DailyLog`、`FoodItem`、`ExerciseItem` 等业务表继续作为事实来源。记忆层只保存 Agent 需要的状态、摘要和偏好。

例如“用户今天摄入了多少热量”必须实时查询业务数据，不能相信一条旧记忆；“用户乳糖不耐受”可以作为长期语义事实，但要保留来源、置信度、是否确认和有效期。

### 上下文如何组装？

当前上下文大致由以下部分组成：

```text
静态角色与安全 Prompt
+ 已确认的长期语义事实
+ 今日/本周实时业务状态
+ 当前会话的工作状态
+ 近期 HumanMessage / AIMessage
+ 本轮用户消息
```

近期历史受条数和 8000 字符预算限制，不再把原始历史全部拼进 System Prompt。这样既降低上下文长度，也避免把历史用户输入错误提升为系统指令。

### 与旧面试稿的差别

旧稿把三层记忆描述成“用户画像、统计、对话摘要”，并声称超过 10 条后会自动调用 LLM 压缩。当前生产实现不是这个结构：画像和统计属于上下文数据，真正三层是工作、情景和语义记忆；独立的自动摘要压缩还没有成为主链路。

### 当前限制

- 情景记忆仍复用 `ConversationLog`，还没有独立的 `MemoryEpisode` 实体和相关性检索。
- `ConversationSession.summary` 已预留，但异步摘要和压缩闭环仍需继续建设。
- 当前请求级幂等只保存最近请求游标，不是通用幂等任务表。

## Q8：你是如何解决首 Token 慢和假流式问题的？

### 原因拆解

最初的“流式”不是一条完整的流式链路：

- 专业 Agent 在正文前可能先执行一次完整的 `invoke()` 做工具决策；
- chat 路径会收集完整文本解析意图标记；
- 后端在加载用户数据后才发送第一个 SSE 状态；
- LLM 信号量在返回迭代器时就释放，没有覆盖真实生成阶段；
- `bind_tools()` 返回底层模型对象，可以绕过统一限流；
- 小程序按数组下标更新回复，页面恢复后可能污染历史消息。

### 改造措施

1. 聊天、营养、健身 Agent 的工具决策和最终回答都使用 `.stream()`。
2. 后端在上下文加载前先发送“请求已接收”状态，让用户立即获得反馈。
3. 只缓存必要的控制标记前缀，正文 chunk 到达后立即向上游 yield。
4. 信号量覆盖整个流式迭代生命周期，`bind_tools()` 后继续返回受控代理。
5. 排队回调改为 `ContextVar`，避免并发请求互相覆盖。
6. 小程序通过稳定消息 ID 和请求 ID 更新当前消息，并支持页面切换后恢复流状态。
7. Nginx 关闭代理缓冲，后端设置 `X-Accel-Buffering: no`。

### 如何观测首 Token？

同一个 `request_id` 下记录：

```text
request_received
auth_completed
context_loaded
route_completed
llm_request_started
provider_first_chunk
provider_first_reasoning
provider_first_content
application_first_token
response_completed
```

这样可以区分是应用准备慢、模型排队慢、模型推理慢，还是反向代理缓冲。

### 不应夸大的地方

目前有阶段耗时日志，但还没有 Prometheus 指标、可视化仪表盘和正式告警；也没有足够生产样本证明 P50 已达到某个固定目标。面试时应说“具备定位能力并消除了已知阻塞点”，不要直接承诺一个没有统计依据的数字。

### 关于模型思考过程

当前 `glm-5.3-flash` 不支持关闭思考，配置为 `reasoning_effort=low`。后端只透传 API 实际返回的 `reasoning_content`，前端单独展示；思考内容不写入会话历史或长期记忆。

## Q9：工具调用如何保证安全、幂等和数据一致性？

### 身份安全

JWT 鉴权后，FastAPI 将 `user_id`、`session_id` 和 `request_id` 写入请求级 `RequestContext`。工具通过 `ContextVar` 获取服务端绑定的用户身份，而不是相信模型传入的 `user_id`。

这解决的是一个关键问题：模型可以建议调用什么工具、填什么业务参数，但不能决定操作哪个用户的数据。

### 请求级幂等

客户端为每次聊天生成稳定 `request_id`。如果网络超时后重试同一请求，服务端检测到该会话最近已经完成相同请求，就直接回放之前结果，避免再次执行记录工具。

当前实现适合处理小程序的即时重试，但还不是支持任意历史请求的完整幂等表。

### 数据库一致性

- `daily_logs` 增加 `(user_id, date)` 唯一约束，避免并发创建两条当天汇总。
- 饮食和运动写入限制在当前用户范围内。
- 更新、删除后重新计算汇总，避免累计误差。
- 后台线程单独创建数据库 Session，不复用请求线程 Session。
- 数据库迁移通过独立脚本执行，而不是依赖 `create_all()` 修改已有表。

### 食物缓存为什么需要重构？

旧表只按食物名称去重，“苹果一份 70 卡”和“苹果一个 100 卡”会被当成冲突数据。新结构使用：

```text
normalized_name + basis_type + portion_unit
```

其中 `basis_type` 区分：

- `per_100g`
- `per_100ml`
- `per_unit`
- `legacy_unknown`

固体使用每 100g，液体使用每 100ml；产品规则允许液体查询按 `1g = 1ml` 映射。未知食物估算增加 `pending / ready / failed` 状态，失败或超时后不会永久显示“计算中”。

## Q10：RAG 系统是怎么设计和评估的？

### 生产主链路

```text
知识文档
→ Markdown/通用文档加载
→ 标题感知和语义分块
→ 清洗去重
→ embedding-3 向量化
→ Chroma 持久化

用户查询
→ 向量召回 + BM25 关键词召回
→ RRF 融合排序
→ 可选 Jina Reranker
→ 返回给 Agent 作为依据
```

项目代码还支持 Query Expansion、HyDE、CoT、Self-RAG 和 Agentic RAG，但这些是可选能力，生产默认没有全部开启。面试时不能把“代码中存在”说成“每次请求都在使用”。

### 为什么使用混合检索？

- 向量检索适合语义相近但表述不同的问题。
- BM25 对动作名、食物名和专业术语的精确匹配更稳定。
- RRF 用排名而不是直接混合不同量纲的分数，降低调参复杂度。

### 当前索引配置

- Embedding：`embedding-3`
- 维度：2048
- API 单批输入上限：64
- 文档索引属于派生数据，不提交 Git，应在目标环境重新构建。

### 如何评估？

项目使用 RAGAS 思路评估四个维度：

| 指标 | 主要判断 |
| --- | --- |
| Faithfulness | 回答中的声明能否由检索内容支持 |
| Answer Relevancy | 回答是否真正回应用户问题 |
| Context Precision | 相关上下文是否排在前面 |
| Context Recall | 检索内容是否覆盖参考答案中的要点 |

当前 `eval_dataset.json` 实际有 15 条数据。仓库中的旧 quick report 只跑了 5 条，并且只产生 Faithfulness 和 Answer Relevancy 两项有效结果，不能拿旧稿中“Self-RAG 0.92”等数字作为项目实测结论。

更准确的面试说法是：

> 我搭建了可重复的 RAG 评测流程，能够区分检索失败、排序失败和生成失败；当前数据集规模还小，已有结果只作为工程基线，不作为产品效果证明。后续需要扩大真实问题集，并按路由、安全和不同知识类别分层评估。

## Q11：开发过程中遇到过哪些困难或线上故障？如何解决？

面试时建议选择一到两个讲深，不要一次罗列所有问题。

### 故障一：历史消息被当成当前回复连续改写

**现象**：用户发起新问题后，之前的历史消息也开始显示成新回复，页面出现连续输出。

**定位**：后端 SSE 本身按顺序返回，但小程序使用消息数组下标定位当前 AI 消息。历史加载、页面切换和新流并发发生时，数组位置变化，后续 chunk 写到了错误消息。

**处理**：

- 每条消息生成稳定 ID；
- 每次流请求生成独立 request ID；
- 只有当前活跃请求可以更新对应 AI 消息；
- 页面隐藏和恢复时保存流状态，而不是重新绑定到数组末尾；
- 历史消息过滤未完成的临时流对象。

**结果**：流式内容只更新当前消息，历史加载和页面切换不再污染旧消息。

### 故障二：用户感觉首 Token 很慢

**现象**：界面长时间显示“Agent 正在思考”，随后正文快速出现。

**定位**：问题不是单一模型慢，而是路由、上下文查询、阻塞式工具决策、完整文本缓存和 Nginx 缓冲叠加。

**处理**：将首轮工具决策和最终回答改成真实流式；请求进入后先发送状态；修复信号量生命周期和 `bind_tools()` 绕过；增加 provider/application 两级首 Token 日志；关闭 Nginx buffering。

**结果**：消除了应用层已知的假流式，能够精确区分模型等待和应用等待。工具参数仍需完整后才能执行，这是工具调用本身的合理停顿。

### 故障三：食物缓存迁移发现重复名称

**现象**：迁移脚本发现“苹果”“鸡蛋”存在重复名称而停止，旧数据中同时存在每份、每个、空单位和不同来源。

**定位**：问题不是简单的重复行，而是原表没有表达热量基准，名称唯一约束把不同口径错误地混为一类。

**处理**：不直接猜测合并结果，而是备份旧表并重建缓存结构；增加规范化名称、基准类型、单位和来源；导入版本化常见食物数据；人工数据优先于参考数据，参考数据优先于 API 和 LLM。

**结果**：同一种食物可以安全保存每 100g、每 100ml 或每单位热量，不再依赖模糊“份”的含义。

### 故障四：Chroma 报 1024 与 2048 维度不匹配

**现象**：线上日志出现：

```text
Collection expecting embedding with dimension of 1024, got 2048
```

**定位**：运行时已经切换到默认 2048 维的 `embedding-3`，但持久化 Chroma 集合仍是以前 `embedding-2` 建立的 1024 维索引。即使把新模型强制设为 1024 维，也不能复用旧模型生成的向量空间。

**处理**：停止服务、保留旧索引备份、从源文档全量重建。第一次重建又发现智谱单次最多接收 64 条输入，因此把 `OpenAIEmbeddings.chunk_size` 固定为 64，并修复 `force_rebuild` 参数没有向下传递的问题。

**验证**：检查 Chroma SQLite 元数据确认维度为 2048、文档块数量正确，再执行真实相似度查询，确认返回知识库中的牛奶相关内容，最后启动 4 个 Gunicorn worker 并检查日志。

### 故障五：未知食物永久显示“计算中”

**现象**：记录未知食物后，后台 LLM 估算失败或进程重启，前端一直显示“计算中”。

**定位**：原流程只有“是否算出热量”，没有持久化任务状态和失败终态。

**处理**：为 `FoodItem` 增加 `pending / ready / failed` 状态；后台任务无论成功、异常或超时都写入终态；读取记录时将超时 pending 转为 failed。

**结果**：用户能看到明确失败状态，可以重试，不会永久卡住。

### 通用故障回答框架

```text
现象：用户看到了什么
→ 证据：日志、数据库、网络或 UI 状态说明什么
→ 根因：哪个组件的什么假设失效
→ 修复：为什么选择这个方案
→ 验证：如何证明不仅是“服务启动了”
→ 预防：测试、约束、监控或迁移如何避免复发
```

## Q12：架构升级后，项目为什么更容易维护？

### 推荐回答

维护性的提升主要来自边界变清楚，而不是代码量变少。

- 身份边界：用户身份统一来自服务端请求上下文。
- 路由边界：规则只负责高确定性任务，LLM 处理模糊语义。
- 数据边界：业务表保存事实，记忆保存 Agent 上下文，RAG 保存外部知识。
- 配置边界：`config.yaml` 管非敏感行为，dotenv 管密钥。
- 环境边界：dev/prod profile 明确，本地脚本不会改变服务器 systemd 启动方式。
- 协议边界：SSE 事件类型和消息 ID 固定，前后端可以分别测试。
- 部署边界：`main` 用于开发，`deploy` 是服务器快照，迁移在重启前显式执行。

以前出现问题时，通常需要猜“是不是模型不稳定”；现在可以根据 request ID 和阶段日志定位到具体层级，也能用确定性测试覆盖路由、鉴权、缓存和数据约束。

### 仍需继续拆分的地方

`backend/app/main.py` 仍承担 API、部分业务逻辑、模型估算和后台任务，后续应逐步拆成 router、application service、domain service 和 infrastructure，而不是继续扩大主文件。

## Q13：你如何验证修改真的在本地和生产生效？

### 本地验证

- 使用 `config.yaml` 的 dev profile 和 `.env.dev`，避免连接生产数据库。
- 运行 `python -m compileall` 和 `git diff --check`。
- 根据改动范围运行 unittest；当前维护基线为 185 项。
- 对路由反例、重复请求、数据库约束、SSE 分块和前端消息恢复做针对性测试。

### 生产验证

生产链路是：

```text
Nginx
→ 127.0.0.1:8000
→ systemd 管理的 Gunicorn
→ 4 个 UvicornWorker
→ FastAPI
```

发布时由 `deploy` 分支进入服务器，`update.sh` 拉取固定分支、安装依赖、停止服务、执行迁移，再重启服务。

不能只看 `systemctl active`，还要检查：

- 服务器实际 Git commit；
- 4 个 worker 是否全部完成启动；
- API 是否返回正确状态；
- 数据库迁移结果；
- SSE 是否分块到达；
- RAG 集合维度、数量和真实查询；
- 日志中是否出现 Traceback、超时或降级。

## Q14：为什么保留 LangGraph，而没有重写成其他 Agent 框架？

### 推荐回答

原项目已经有 LangGraph 状态、专业 Agent 和工具体系。升级的主要问题是路由、会话、安全、流式和数据一致性，而不是框架本身。

如果此时切换 CrewAI、AutoGen 或其他框架，会同时引入状态迁移、工具协议迁移和回归风险，却不能自动解决业务身份与数据一致性。因此我选择复用现有 `graph.py`、`LLMManager`、`MemoryManager` 和工具，在关键边界上渐进式改造。

当前非流式接口继续使用完整 LangGraph 和 Expert Review；线上小程序主要使用的流式接口走独立低延迟路径，避免评审循环阻塞首 Token。代价是两条路径需要持续做一致性测试，后续可以逐步提取共享的路由、工具执行和状态模块。

### 什么情况下会考虑 LangGraph Checkpointer？

当训练计划调整、器械识别确认或长任务需要暂停、等待用户确认并恢复时，Checkpointer 才能体现价值。但 checkpoint 不能替代业务数据库的授权、事务和版本控制。

### 不建议的旧表述

不要说“如果重做就一定切到 Swarm + MCP”。框架选择应由任务状态复杂度决定；MCP 是工具互操作协议，也不等于完整的业务编排和持久化方案。

## Q15：Prompt 和上下文是如何设计的？

### 当前结构

```text
静态 System Prompt
  角色、能力、工具规则、安全边界

+ 受控动态上下文
  已确认语义事实
  今日/本周业务状态
  当前会话工作状态
  近期规范角色消息

+ 当前用户消息

+ 工具或 RAG 结果
```

### 关键原则

1. System Prompt 只放高优先级规则，不直接拼接原始用户历史。
2. 用户画像、统计和长期事实按任务需要注入，并设置上下文预算。
3. 工具结果与模型建议区分，模型不能把“建议执行”说成“已经执行”。
4. 写操作必须由结构化参数、服务端身份和数据库结果共同确认。
5. RAG 是依据来源之一，不保证绝对正确；检索为空或冲突时要明确降级。

### 为什么旧稿中的自动摘要说法需要删除？

旧稿描述了“超过 10 条自动生成 100 字摘要”的伪代码，但当前主链路主要使用近期角色消息和字符预算。面试中只能把异步摘要说成后续优化，不能说成已上线能力。

## Q16：与通用 AI 或传统健身应用相比，产品价值在哪里？

### 推荐回答

我不会简单说通用 AI “不能记忆”或“不能调用工具”，因为不同产品能力会持续变化。更准确的比较方式是看它是否接入本项目的用户数据和业务闭环。

FitCoach 的差异主要在四点：

1. **领域数据连接**：读取用户画像、当天饮食、运动和统计，而不是只依赖当前对话。
2. **真实执行能力**：记录、修改和删除会写入自己的业务数据库，并回读最终状态。
3. **可维护知识**：健身和营养文档可以独立更新并重新索引，不依赖模型重新训练。
4. **持续上下文**：会话状态、历史事件和长期偏好分层维护，并允许用户查看和删除部分语义记忆。

传统健身应用的数据和内容通常更完整，通用 AI 的基础模型能力也更强。FitCoach 当前优势不是规模，而是尝试把“对话、专业知识和用户行为数据”连接成一个可执行闭环。

## Q18：当前项目还有哪些不足？下一步怎么做？

### 已知不足

- 还没有完整的主教练多步骤规划、动态重路由和任务恢复。
- 器械照片识别、候选确认和教学卡片尚未上线。

- 未接入完整 Metrics、Tracing 和告警系统。
- `main.py` 职责仍然偏重。
- 后台食物估算仍使用进程内任务，进程重启后的任务续跑能力有限。

### 下一步优先级

1. 先补 RAG 索引元数据、健康检查和正式迁移机制。
2. 建立器械目录和真实照片评测集，再开发视觉识别闭环。
3. 服务端化训练计划和执行记录，加入版本和回读验证。

### 为什么不是先增加更多 Agent？

因为 Agent 数量不是产品价值。没有身份、状态、事务、评估和回滚，增加 Agent 只会扩大不确定性。下一阶段的目标应该是让用户真正完成“识别器械—理解动作—加入计划—执行训练—获得反馈”的闭环。

## 技术岗深挖问答

这一部分面向 AI 应用工程师和 Python 后端岗位。回答时不要只说“用了 FastAPI、LangGraph、RAG”，而要说明请求怎样流动、状态怎样隔离、故障怎样定位，以及当前方案的边界。

### 技术面试 3 分钟架构说明

可以按下面这条主链路讲：

```text
微信小程序
  → Nginx / HTTPS
  → Gunicorn + UvicornWorker
  → FastAPI 鉴权并加载用户画像、当日数据
  → RequestContext 绑定 user_id / session_id / request_id
  → MemoryManager 组装三层记忆和最近上下文
  → 混合路由判断 chat / nutrition / fitness
  → 专业 Agent 流式调用 GLM，必要时执行数据库或 RAG 工具
  → 工作线程通过 Queue 把增量事件交给异步 SSE 响应
  → 成功后保存对话、工作记忆和路由状态
```

我重点解决的不是“接入一个模型接口”，而是模型接入业务系统后产生的四类工程问题：上下文污染、工具越权与重复写入、流式链路被中间步骤阻塞，以及模型、数据库、向量索引之间的状态一致性。

## Agent 完整请求链路详解（学习版）

这一节不是为了让面试时逐字背诵，而是帮助自己先真正理解系统。整个 Agent 链路可以概括为：请求接入、身份绑定、上下文组装、意图路由、Agent 执行、工具调用、流式返回和状态持久化。

```text
微信小程序
   │
   │ HTTPS + JWT + user_message/session_id/request_id
   ▼
Nginx
   ▼
Gunicorn（4 workers）
   ▼
UvicornWorker + FastAPI
   │
   ├─ JWT 鉴权
   ├─ 加载用户画像、今日饮食/运动统计
   └─ 创建 SSE 流式响应
   ▼
后台工作线程
   │
   ├─ RequestContext 身份绑定
   ├─ MemoryManager 三层记忆加载
   ├─ 最近对话上下文组装
   ├─ 幂等请求检查
   └─ 混合路由
        ├─ chat
        ├─ nutrition
        └─ fitness
             │
             ├─ GLM-5.3-Flash
             ├─ 数据库工具
             └─ RAG 检索工具
                    ├─ Chroma
                    ├─ BM25
                    ├─ RRF
                    └─ Jina Reranker
   ▼
Agent 增量输出
   ▼
线程安全 Queue
   ▼
FastAPI SSE
   ▼
Nginx 禁止缓冲
   ▼
微信小程序增量更新当前消息
   │
   └─ 成功后回写对话、工作记忆和路由状态
```

### 1. 请求入口：从小程序进入后端

小程序向流式接口发送用户问题，并携带三个重要标识：

- JWT Token：证明当前登录用户身份；
- `session_id`：区分用户的不同对话会话；
- `request_id`：追踪单次请求，也用于超时重试时避免重复执行。

生产环境中，请求首先经过 Nginx 的 HTTPS 和反向代理，然后进入由 systemd 管理的 Gunicorn。Gunicorn 启动 4 个 UvicornWorker，每个 worker 运行 FastAPI ASGI 应用。

```text
微信小程序 → Nginx → Gunicorn → UvicornWorker → FastAPI
```

FastAPI 在接口入口完成 JWT 鉴权。后续使用的 `user_id` 来自服务端解析后的 Token，而不是前端请求体，更不会采用模型自己生成的用户 ID。这是工具安全的第一道边界。

流式入口主要位于 [`backend/app/main.py`](../../backend/app/main.py)。

### 2. 加载请求级业务上下文

鉴权成功后，API 会从 PostgreSQL 加载本次回答需要的结构化数据，例如：

- 用户身高、体重、目标和基础资料；
- 当日饮食记录和热量摄入；
- 当日运动记录和热量消耗；
- 其他生成个性化建议需要的业务统计。

这些内容是结构化业务事实，不属于自然语言记忆。例如“今天已经摄入多少千卡”应通过数据库聚合得到，不能让模型从历史摘要中猜测。

加载完成后，入口会提前关闭鉴权阶段使用的 SQLAlchemy Session。原因是流式生成可能持续几十秒，如果每个请求在模型等待期间都长期占有数据库连接，高并发时连接池很容易被耗尽。后续工具需要访问数据库时，再自行创建短生命周期 Session。

这也避免把同一个 SQLAlchemy Session 从 FastAPI 请求线程传给后台工作线程，因为 Session 本身不适合跨线程共享。

### 3. 建立 SSE 和同步—异步桥接

接口返回 `text/event-stream` 类型的 `StreamingResponse`。服务端会先发送一个 `status` 事件，使小程序尽快知道请求已被接收，而不是一直显示无反馈的等待状态。

现有 LangChain 和 Agent 代码以同步 Python Generator 为主，FastAPI 的流式出口是异步生成器。项目使用“后台工作线程 + `queue.Queue`”完成桥接：

```text
同步 Agent Generator
        │
        ▼
后台工作线程
        │ q.put()
        ▼
queue.Queue
        │ run_in_executor 等待
        ▼
FastAPI Async Generator
        │
        ▼
SSE Response
```

工作线程负责阻塞式模型迭代和 Agent 执行，FastAPI 事件循环只负责消费队列、编码 SSE 和写回客户端，因此同步模型 SDK 不会直接阻塞 ASGI 事件循环。

当前协议区分多种事件：

| SSE 事件 | 作用 |
| --- | --- |
| `status` | 上下文加载、路由、处理进度等用户可理解状态 |
| `queue` | 当前模型调用正在排队及排队位置 |
| `thinking` | 模型 API 实际返回的 `reasoning_content` |
| `intent` | 路由或记录行为产生的结构化意图 |
| `data` | 用户最终看到的正文增量 |
| `[DONE]` | 本次流式响应正常或异常结束 |

响应头包含 `X-Accel-Buffering: no` 和 `Cache-Control: no-cache`，避免 Nginx 将多个模型 chunk 聚合成大块后再返回。队列 30 秒没有新消息时，服务端会发送 SSE 注释心跳维持连接。

### 4. RequestContext：绑定可信请求身份

进入后台线程后，系统会创建请求级上下文：

```python
RequestContext(
    user_id=current_user.id,
    session_id=session_id,
    request_id=request_id,
)
```

它使用 Python `ContextVar` 保存，使同一 worker 中并发执行的请求不会通过普通全局变量共享身份和状态。流式任务会在线程内部重新建立上下文，不依赖上下文自动跨线程传播。

工具执行时会调用 `get_effective_user_id()`。如果 RequestContext 已经绑定用户，就优先使用服务端身份；只有脚本或单元测试直接调用工具、没有请求上下文时，才使用显式传入的 ID。

因此，即使模型生成了下面的 Tool Call：

```json
{
  "user_id": 999,
  "food_name": "牛奶"
}
```

工具最终仍然操作 JWT 对应的当前用户，而不是用户 999。这个设计防止 Prompt Injection 或模型幻觉导致跨用户读写。

实现位于 [`backend/app/runtime_context.py`](../../backend/app/runtime_context.py)。

### 5. MemoryManager：加载三层记忆

请求身份绑定后，MemoryManager 会加载工作记忆、情景记忆和语义记忆。

#### 工作记忆

工作记忆保存在 `ConversationSession.working_memory_json`，主要记录：

- 最近一次用户输入和 Agent 回答；
- 上一次使用的专业 Agent；
- 最近一次路由结果；
- 当前会话意图和模式；
- 最近成功处理的 `request_id`。

它用于理解“第二个呢”“换成哑铃”“那晚餐呢”这类依赖最近状态的短输入。

#### 情景记忆

情景记忆来自 `ConversationLog`，保存每一轮真实对话的用户问题、Agent 回答、Agent 类型、时间和 `session_id`。它提供可回放的近期经历，而不是只保存一段不可核验的摘要。

#### 语义记忆

语义记忆保存在 `UserMemory`，用于记录跨会话较稳定的用户事实，例如健身目标、饮食偏好、训练限制和长期习惯。`(user_id, memory_key)` 唯一约束防止同一个语义键无限重复。

#### 上下文组装预算

当前请求默认读取最近 30 天内最多 8 轮对话。单条内容最多保留 2000 字符，最终消息序列还要满足 8000 字符总预算；超出预算时从最旧消息开始移除。当前用户问题始终保持为最后一个 `HumanMessage`。

```text
System Prompt
HumanMessage（历史）
AIMessage（历史）
...
HumanMessage（当前问题）
```

这样既能让 Agent 理解会话，又不会把整个对话数据库全部塞进 Prompt。实现主要位于 [`backend/app/memory/memory_manager.py`](../../backend/app/memory/memory_manager.py)。

### 6. request_id 幂等回放

开始路由前，系统会比较本次 `request_id` 和会话中最近一次成功完成的 `last_request_id`。如果相同，并且工作记忆中仍有对应完整回答，就直接回放上次结果，不再调用模型和写入工具。

它主要解决下面的问题：

```text
小程序等待超时
  → 客户端重试相同请求
  → 后端再次记录同一份饮食或运动
```

当前实现属于轻量的“最近已完成请求幂等”。它还不是完整请求账本：两个完全同时到达、并且都尚未完成的相同 `request_id`，仍有可能一起执行。严格方案应建立带唯一 `request_id` 和 `processing/succeeded/failed` 状态的请求表。

### 7. 混合路由：选择 chat、nutrition 或 fitness

当前路由不是单纯依赖关键词，也不是每个请求都额外调用一次 LLM，而是三层决策：

```text
高确定性规则
   ↓ 未命中
最近上下文和上一轮路由承接
   ↓ 仍不确定
结构化 LLM 语义判断
```

路由输出是结构化对象，而不是只有一个 Agent 名称：

```json
{
  "agent": "nutrition",
  "mode": "single_domain",
  "primary_domain": "nutrition",
  "domains": ["nutrition"],
  "intent": "record",
  "needs_tools": true,
  "needs_clarification": false,
  "safety_flags": [],
  "confidence": 0.95,
  "reason_code": "EXPLICIT_FOOD_RECORD",
  "method": "rule"
}
```

三个 Agent 的基本职责是：

- `chat`：通用健康问答、普通闲聊和需要澄清的问题；
- `nutrition`：食物查询、热量计算、饮食建议和饮食记录；
- `fitness`：训练建议、动作指导、运动记录和健身知识检索。

“记录牛奶 200g”这类目标和实体都明确的操作优先走规则，减少一次模型调用，降低延迟和误写风险。“这样安排合适吗”“第二个动作呢”这类依赖语义和上下文的问题，再由 LLM 判断。

路由器位于 [`backend/app/agents/router.py`](../../backend/app/agents/router.py)。

### 8. Prompt 增强和 AgentState 构建

路由完成后，系统选择对应专业 Agent 的基础 System Prompt，并追加本次请求相关的信息：

- 用户画像和当日业务统计；
- 工作、情景和语义记忆；
- 最近标准消息历史；
- 路由识别出的模式和意图；
- 多领域问题的处理要求；
- 疼痛、伤病等场景的安全边界。

然后构造 AgentState：

```python
{
    "messages": messages_for_prompt,
    "user_id": user_id,
    "user_profile": user_profile,
    "daily_stats": daily_stats,
    "current_agent": agent,
    "retry_count": 0,
    "review_history": [],
    "memory_summary": memory_summary,
    "enhanced_prompts": enhanced_prompts,
    "route_decision": route_result,
}
```

AgentState 将模型消息、确定性业务数据和编排状态分开，避免所有内容都混成一段 Prompt 字符串。

### 9. 专业 Agent 执行和工具选择

#### Chat Agent

Chat Agent 主要处理普通对话和通用健康知识，一般直接进行流式模型生成，不执行有副作用的专业工具。

#### Nutrition Agent

Nutrition Agent 可以查询用户营养信息、食物营养数据、食物热量缓存、当日摄入，并调用工具写入饮食记录。

对“记录牛奶 200g”这类确定性请求，当前有快速路径：

```text
提取食物和重量
  → 查询标准热量或缓存
  → 按实际份量计算
  → 写入 FoodItem / DailyLog
  → 返回记录结果
```

这样可以减少一次模型工具决策，同时避免模型重复调用记录工具。复杂饮食咨询仍通过模型和通用工具循环处理。

#### Fitness Agent

Fitness Agent 可以查询用户健身信息、记录运动，并调用健身知识库工具检索动作方法、训练原则和安全注意事项。涉及专业知识时进入 RAG 链路。

### 10. RAG：从知识库取得可引用依据

Fitness Agent 调用知识库工具后，系统同时执行向量检索与 BM25 关键词检索：

```text
用户查询
   ├─ Chroma 向量检索：语义、同义表达
   └─ BM25 关键词检索：动作名、肌肉名、精确术语
          │
          ▼
      加权 RRF 融合
          │
          ▼
    可选 Jina Reranker
          │
          ▼
       Top-K 文档
```

检索数量已经从代码中的隐式倍率改为配置项。当前生产链路由 Agent 请求 5 条结果，
向量和 BM25 各召回最多 30 条，RRF 融合后保留 15 条给 Jina，重排返回 5 条；
统一上下文整理器过滤错误、广告和高度相似内容后，最终最多选 3 条、合计不超过
1500 字符交给 LLM。开发环境关闭重排，向量和 BM25 各召回最多 10 条。

两路结果按照排名使用加权 RRF 融合：

```text
score(d)
  = 0.5 / (60 + vector_rank(d))
  + 0.5 / (60 + bm25_rank(d))
```

RRF 使用名次而不是直接相加原始分数，因为向量距离和 BM25 分数没有统一量纲。
营养和健身 Agent 现在统一使用同一个 RAG 工厂，因此生产重排开关对两条链路
一致生效。Jina 超时从 30 秒降为 5 秒，调用失败会回退到 RRF 初排结果。

当前 Chroma 索引使用 `embedding-3`、2048 维向量，embedding 单批大小固定为 64。索引不会在 4 个 Gunicorn worker 启动时并发重建，而是在部署阶段由独立任务构建。

### 11. LLMManager：模型实例、并发和排队

所有 Agent 通过 LLMManager 获取模型代理。当前主要配置为：

- 模型：`glm-5.3-flash`；
- 思考模式：开启；
- 推理强度：`low`；
- 请求超时：30 秒；
- 重试次数：最多 2 次。

LLMManager 按 temperature 在单个进程内缓存模型客户端，减少重复初始化。每个 Gunicorn worker 使用 `threading.Semaphore(3)` 限制最多 3 个并发 LLM 调用。

由于生产环境有 4 个 worker，理论上的全服务并发上限是：

```text
4 workers × 3 calls per worker = 12 个模型调用
```

这个 Semaphore 是进程内限流，不是全局分布式限流；排队位置也只代表当前 worker。未来如果扩展到多机器，需要把配额和队列迁移到 Redis 或独立模型网关。

流式调用中，Semaphore 许可覆盖整个生成器消费周期。只有模型流完全结束或发生异常后，才在 `finally` 中释放，防止 `stream()` 刚返回迭代器时就提前释放许可。

`bind_tools()` 会返回新的 LangChain Runnable，因此工具绑定后的 Runnable 也会被重新包装，确保不会绕过统一并发控制和耗时日志。实现位于 [`backend/app/llm_manager.py`](../../backend/app/llm_manager.py)。

### 12. 流式 Tool Call：先合并参数，再执行工具

模型生成工具调用时，工具名称、调用 ID 和 JSON 参数可能被拆分到多个 chunk 中：

```text
chunk 1: tool_name=log_food...
chunk 2: _intake, args={"food...
chunk 3: _name":"牛奶","weight":200}
```

如果收到第一段就执行，工具会拿到不完整甚至非法 JSON。项目中的 `StreamedToolCall` 会同时完成两件事：

1. 将 provider chunk 中的思考或可见正文立即向上游转发；
2. 使用 LangChain `AIMessageChunk` 的加法语义持续合并 chunk。

第一轮流结束后，系统将累积结果还原为包含完整 `tool_calls` 的 `AIMessage`，然后执行工具，把工具结果加入消息列表，再发起第二轮模型流式调用：

```text
第一轮模型流
  → 生成 Tool Call
  → 合并完整工具参数
  → 执行数据库或 RAG 工具
  → ToolMessage 加入上下文
  → 第二轮模型流
  → 生成面向用户的最终答案
```

因此这里的含义是“模型响应真实流式，工具参数完整后执行”，并不是边接收半截 JSON 边执行副作用。相关实现位于 [`backend/app/agents/base.py`](../../backend/app/agents/base.py)。

### 13. 增量结果如何到达小程序

模型每返回一个 chunk，就沿以下链路传播：

```text
GLM Provider Chunk
  → Agent Generator
  → 工作线程 q.put()
  → FastAPI Async Generator
  → SSE Data Frame
  → Nginx
  → 微信小程序
```

后端同时记录 provider 第一个 chunk、第一个 reasoning chunk、第一个正文 chunk、API 第一次发送正文和完整请求耗时。这样可以区分“状态提示已经出现”和“模型真正开始回答”，并判断延迟来自上下文加载、路由、排队、模型还是工具。

小程序端只把正文 chunk 追加到当前正在生成的 assistant 消息；历史消息保持只读。收到 `[DONE]` 后，将当前消息从生成中状态更新为完成。这样避免以前使用共享索引或错误消息引用时，历史消息也被不断改写的问题。

### 14. 最终结果回写：业务事实和对话记忆分开

最终回写分为两条路径。

#### 业务事实即时写入

饮食和运动工具执行时，直接写入结构化业务表，例如：

- `FoodItem`：具体食物摄入；
- `ExerciseItem`：具体运动记录；
- `DailyLog`：用户当天的聚合记录；
- `FoodCalorieCache`：有明确计量口径的食物热量数据。

这些副作用在工具执行时完成，不能等聊天结束后再从自然语言答案反向解析。

数据库通过唯一约束、检查约束和事务重试维护一致性。例如 `DailyLog` 的 `(user_id, date)` 唯一；并发创建同一天记录时，一个事务触发 `IntegrityError` 后回滚并重新查询已经创建的行。

食物估算使用 `pending/ready/failed` 状态。开始估算写 pending，成功写 ready，异常写 failed，前端因此不会永久停留在“计算中”。

#### 对话和记忆在成功后写入

Agent 完整生成成功后，MemoryManager 才保存：

- `ConversationLog` 中的用户问题和完整回答；
- `ConversationSession` 中的最后 Agent、工作记忆和 `last_request_id`；
- 上一轮路由的领域、意图和模式；
- 必要时更新 `UserMemory` 中的稳定长期事实。

如果模型或工具中途异常，错误内容会返回客户端，但不会保存为成功对话，避免下一轮模型把错误提示当成可信历史继续强化。

### 15. LangGraph 完整图和线上流式路径的关系

项目保留的非流式 LangGraph 完整路径为：

```text
START
  → router
  → chat → END
  → nutrition → expert_review → retry / END
  → fitness   → expert_review → retry / END
```

线上 SSE 主路径复用了路由、记忆、专业 Agent 和工具，但没有等待生成后的 Expert Review。原因是正文一旦已经流给用户，就无法在评审不通过时撤回；如果等评审和重试全部完成再发送，用户看到的又会变成高延迟的假流式。

当前工程取舍是：

- 非流式完整图侧重专家评审和重试；
- 线上流式路径侧重首 Token 和实时反馈；
- 简单确定性记录通过快速路径降低延迟和重复写入风险。

后续更理想的结构是把质量控制拆成生成前约束、流中安全拦截和生成后异步质检，再逐步统一两条执行路径。

| LLMManager | 模型复用、并发限制、排队反馈和分段耗时日志 |
| StreamedToolCall | 工具参数 chunk 合并、多轮模型—工具执行 |
| SQLAlchemy/PostgreSQL | 用户、业务事实、会话、对话和长期记忆持久化 |
| Chroma | 2048 维健身知识向量检索 |
| BM25 + RRF | 关键词检索和多路候选排名融合 |
| Jina Reranker | 可选的候选结果二次语义重排 |

### 对整条链路的一句话总结

> FitCoach 不是简单把用户问题转发给大模型，而是以 FastAPI 为请求入口，通过 RequestContext 绑定可信身份，利用三层记忆和混合路由构造上下文，再由专业 Agent 调用模型、数据库和 RAG 工具；模型 chunk 通过线程队列桥接成 SSE 实时返回，成功后分别回写业务事实、对话历史和会话状态，从而形成完整的感知、决策、执行和记忆闭环。

## Q21：一次聊天请求在后端内部是如何执行的？

### 推荐回答

请求进入 `/api/chat/stream` 后，首先由 FastAPI 完成 JWT 鉴权，生成或接收 `request_id` 和 `session_id`，并读取用户画像与当日统计。因为流式请求可能持续几十秒，我在进入生成阶段前主动释放鉴权阶段使用的数据库 Session，避免长连接占满连接池。

之后在后台工作线程中执行同步 Agent 生成器：

1. 用 `ContextVar` 绑定服务端确认过的用户、会话和请求身份；
2. 加载工作记忆、情景记忆和语义记忆；
3. 构建受条数和字符预算限制的消息历史；
4. 通过规则优先、LLM 兜底的混合路由选择专业 Agent；
5. Agent 流式调用模型，必要时收集工具参数、执行工具，再继续生成；
6. 工作线程把 `status`、`queue`、`thinking`、`intent`、`data` 事件放入线程安全队列；
7. FastAPI 异步生成器持续消费队列并编码为 SSE；
8. 只有完整成功的回答才写入长期对话，错误文本不会进入记忆。

这条链路把 HTTP 生命周期、Agent 业务编排和模型同步 SDK 隔开了，方便分别观测和测试。

### 技术追问：为什么不用同一个数据库 Session 跑完整个流？

因为 SQLAlchemy Session 不是跨线程安全对象，而且模型生成期间并不需要一直持有鉴权阶段的连接。提前关闭后，每个工具自己创建短生命周期 Session，可以减少连接占用，也避免把请求级 Session 传入后台线程。

## Q22：LangGraph 在项目中承担什么职责？为什么线上流式路径没有直接跑完整图？

### 当前图结构

非流式路径使用 `StateGraph`，状态中包含：

- `messages`：LangChain 标准消息；
- `user_id`、用户画像和当日数据；
- `current_agent` 和结构化路由决策；
- `retry_count`、`review_history`、`skip_review`；
- 记忆摘要和增强后的系统提示词。

图的基本路径是：

```text
START → router → chat → END
                 ├→ nutrition → expert_review → retry / END
                 └→ fitness   → expert_review → retry / END
```

线上 SSE 使用独立的低延迟执行路径，但复用了同一套路由、记忆、Agent 和工具。原因是完整图中的专家评审会在正文生成后再增加一次甚至多次模型调用，如果等待评审完成再返回，用户会感到“假流式”；如果正文已经发出，又无法撤回低分答案。

因此当前取舍是：

- 非流式完整图保留评审与重试能力；
- 流式主链路优先首包速度，跳过事后专家评审；
- 简单事实查询还有快速通道，避免无必要的评审调用。

### 这个设计的边界

两条路径可能产生行为差异。后续更合理的方向是把“生成前检查、流中安全拦截、生成后异步质检”拆开，并统一成可流式执行的状态机，而不是长期维护两套编排逻辑。

## Q23：所谓“真实流式”具体是怎样实现的？

### 推荐回答

真实流式不是服务端拿到完整回答后再按字符切片，而是直接迭代模型 SDK 返回的 chunk，每得到一个 chunk 就向上游发送。

项目里有三段连续流：

```text
模型 chunk
  → Agent Python generator
  → 后台线程 Queue
  → FastAPI async generator
  → SSE
  → 微信小程序增量渲染当前 assistant 消息
```

FastAPI 入口会先立即发一个 `status` 事件，让用户知道请求已被接收。模型返回的 `reasoning_content` 和可见正文分别编码成 `thinking` 与普通 `data` 事件；结束时发送 `[DONE]`。响应头设置 `X-Accel-Buffering: no`，避免 Nginx 把上游 chunk 缓冲成大块后再返回；30 秒无数据时发送 SSE 注释心跳。

### 为什么要用“线程 + Queue”？

现有 LangChain/Agent 调用链是同步生成器，而 FastAPI 的流式响应是异步生成器。工作线程负责阻塞式模型迭代，`queue.Queue` 负责跨线程传递事件，事件循环只负责等待队列和写 SSE，因此不会直接被同步 SDK 阻塞。

### 如何定义和测量首 Token？

项目分别记录：

- HTTP 请求开始到上下文加载完成；
- 路由完成耗时；
- 模型调用开始到 provider 第一个 chunk；
- 第一个 reasoning chunk；
- 第一个可见正文 chunk；
- API 第一次向客户端发正文的时间；
- 完整请求耗时。

这样能区分“状态首包很快”和“真正正文首字很快”，也能判断延迟来自记忆、路由、排队、模型还是工具。

### 当前仍可改进的地方

当前线程队列没有严格的容量和客户端断开传播机制。高并发下应增加有界队列、取消信号、断连检测，并评估原生异步模型客户端，减少线程数量。

## Q24：流式工具调用怎样处理？工具参数被拆成多个 chunk 时会不会执行错误？

### 推荐回答

工具调用和普通文本不同：模型可能把工具名、调用 ID 和 JSON 参数拆散到多个 chunk 中，所以不能收到第一小段参数就执行。

项目中的 `StreamedToolCall` 会：

1. 对 `bind_tools()` 后的 Runnable 调用 `stream()`；
2. chunk 到达后立即向上游转发其中的思考或正文；
3. 同时利用 LangChain `AIMessageChunk` 的加法语义增量合并 chunk；
4. 流结束后还原出包含完整 `tool_calls` 的 `AIMessage`；
5. 再执行工具，把结果作为 ToolMessage 放回消息列表；
6. 发起下一轮模型流式调用，生成面向用户的最终答案。

因此它是“模型输出真实流式，工具参数完整后执行”，并不是边接收半截 JSON 边调用工具。

对于“记录牛奶 200g”这类意图和实体都很明确的写操作，营养 Agent 还有确定性快速路径：直接使用现有解析器和记录工具，减少一次模型决策并降低重复执行概率。复杂营养咨询仍走通用工具循环。

### 为什么 `bind_tools()` 之后还要重新包装？

LangChain 的 `bind_tools()` 会返回新的 Runnable。如果只给原始 LLM 加并发代理，绑定工具后的对象可能绕过限流。当前实现会把新 Runnable 再包装成统一代理，保证 `invoke`、`stream` 和工具绑定调用使用同一套并发控制和日志。

## Q25：模型并发、排队和多进程隔离是怎样设计的？

### 当前实现

`LLMManager` 按 temperature 在单个进程内缓存模型客户端，减少重复初始化。每个进程使用 `threading.Semaphore(3)` 限制同时进行的模型调用；如果没有许可，请求进入等待计数，并通过 SSE `queue` 事件告诉前端当前排队位置。

流式调用有一个容易出错的细节：许可必须覆盖“完整消费生成器”的生命周期，不能在 `stream()` 返回迭代器时就释放。因此代理在内部 `iterate()` 的 `finally` 中释放 Semaphore，即使中途异常也不会永久泄漏许可。

### 多进程下如何计算？

Semaphore 是进程内对象。生产环境有 4 个 Gunicorn worker，所以理论最大并发模型调用数不是 3，而是 `4 × 3 = 12`；队列位置也只反映当前 worker，而不是全实例全局队列。

面试时应主动说明这个边界：当前方案适合单机小流量保护，若要严格执行全局 QPS、租户配额或多实例公平队列，应把许可和排队状态移到 Redis 等共享系统，或使用独立推理网关。

### `ContextVar` 在这里有什么作用？

请求身份和排队回调都使用 `ContextVar`，确保同一 worker 内并发请求不会共享可变全局变量。流式任务进入后台线程后，会在线程内部重新建立请求上下文，避免依赖事件循环线程的隐式上下文传播。

## Q26：三层记忆在代码和数据库中分别怎样实现？

### 数据模型

| 层级 | 存储 | 作用 | 生命周期 |
| --- | --- | --- | --- |
| 工作记忆 | `ConversationSession.working_memory_json` | 当前会话的最近意图、Agent、末次输入输出、路由状态 | 会话级、频繁更新 |
| 情景记忆 | `ConversationLog` | 每轮用户问题、回答、Agent 类型和时间 | 可回放的对话历史 |
| 语义记忆 | `UserMemory` | 目标、偏好、限制等稳定事实，按 `memory_key` 去重 | 跨会话长期保留 |

用户画像、饮食和运动记录没有塞进自然语言记忆，而是继续保存在结构化业务表中。因为“今天吃了多少”需要精确查询和聚合，不能依赖模型从摘要中猜。

### 上下文预算

当前请求默认查询最近 30 天内最多 8 轮日志，每条内容截断到 2000 字符，并对组装后的消息再施加 8000 字符总预算；超出时从最旧消息开始移除。当前用户消息始终位于最后一个 `HumanMessage`。

这样同时解决了三个问题：不会把整库历史全部塞入 Prompt；角色顺序保持为标准 Human/AI 消息；“第二个呢”“换成哑铃”可以通过最近上下文和上一轮路由继续理解。

### 一致性和并发约束

- `ConversationSession` 对 `(user_id, session_id)` 唯一；
- `UserMemory` 对 `(user_id, memory_key)` 唯一；
- 只有成功完成的回答才保存，防止错误信息进入后续上下文；
- `request_id` 用于最近一次已完成请求的回放。

### 当前局限

字符预算不等于模型 Token 预算；`last_request_id` 也只是轻量的最近请求幂等，不是完整请求账本。后续应使用 tokenizer 做精确预算，引入带唯一键和状态机的 request ledger，并为语义记忆增加来源、置信度、过期时间和用户纠错机制。

## Q27：数据库写入如何处理并发、幂等和缓存口径？

### 每日记录

`DailyLog` 对 `(user_id, date)` 建唯一约束。两个并发请求都发现当天记录不存在时，其中一个 `flush` 可能触发 `IntegrityError`；代码回滚后重新查询已由另一请求创建的行，避免生成两条“今日汇总”。

### 食物热量缓存

旧表只按食物名称唯一，导致“苹果 1 个”“苹果 100g”“牛奶 100ml”互相覆盖。新版缓存把事实拆成：

- `normalized_name`：归一化名称；
- `basis_type`：`per_100g`、`per_100ml`、`per_unit` 或历史未知；
- `portion_qty` 和 `portion_unit`：份量口径；
- 热量、三大营养素、来源与置信信息。

数据库通过检查约束保证口径枚举、份量和热量为正，并用部分唯一索引约束 `(normalized_name, basis_type, portion_unit)`。并发插入同一缓存键时，捕获唯一约束异常后回滚并重新读取胜出的记录。

液体输入按产品约定支持 `g ≈ ml` 映射，但数据库仍保存原始口径，避免把所有食物永久粗暴换算成 100g。

### 异步估算状态

`FoodItem.calorie_status` 只能是 `pending`、`ready`、`failed`。估算开始时是 pending，成功后写 ready，异常后写 failed；前端据此结束“计算中”，失败时允许重试，而不是永久悬挂。

### 幂等边界

当前已能避免“已完成请求重试后再次记录”，但两个完全并发、都尚未完成的相同 `request_id` 仍可能同时执行。技术岗面试中应说明：严格幂等需要单独的请求表，以 `request_id` 唯一约束配合 `processing/succeeded/failed` 状态，并把工具副作用与状态提交放入同一事务或 Outbox/Saga 流程。

## Q28：RAG 的检索、融合和索引生命周期是怎样设计的？

### 检索链路

项目同时执行向量检索和 BM25：向量检索负责同义表达和语义相似，BM25 负责动作名、肌肉名等精确关键词。各层候选数不再依赖隐藏的 `top_k × 2/3`，而是由 `config.yaml` 明确配置。生产环境两路各取最多 30 条，使用加权 RRF 融合并保留 15 条候选：

```text
score(d) = 0.5 / (60 + rank_vector(d))
         + 0.5 / (60 + rank_bm25(d))
```

代码中的 rank 从 1 开始；没有进入某一路候选的文档不获得该路分数。RRF 使用名次而不是直接混合两种不可比的原始分数。生产环境对 15 条候选启用 Jina Reranker，得到 5 条结果，再经过统一去重和字符预算后最多把 3 条交给 LLM。营养和健身 Agent 共用同一实例和配置；Jina 5 秒内失败则回退 RRF。Query Expansion、HyDE、CoT 和 Self-RAG 虽有模块，但生产默认没有全部打开。

### Embedding 维度故障说明

Chroma collection 建立后，其向量维度固定。把旧的 1024 维模型改成 `embedding-3` 2048 维后，如果继续复用旧 collection，就会出现：

```text
Collection expecting embedding with dimension of 1024, got 2048
```

这不是查询代码的类型错误，而是模型配置和持久化索引不兼容。处理方式是备份旧索引，从原始知识文档全量重建，不能只修改环境变量。智谱接口单批最多 64 条，因此 embedding 客户端批量大小固定为 64。

### 为什么生产启动时不自动建索引？

Gunicorn 有 4 个 worker。如果每个 worker 启动时都检查甚至重建同一个 Chroma 目录，会重复消耗 API、延长启动并产生文件竞争。因此生产配置关闭 `rag_startup_index`，索引更新作为部署阶段的独立任务执行。

### 还应怎样完善？

为索引保存 manifest：知识库版本、embedding 模型、维度、chunk 参数、构建时间和文档哈希。服务启动只做兼容性校验；新索引构建完成后使用版本目录或蓝绿切换原子替换，避免边服务边覆盖。

## Q29：配置、进程模型和数据库连接池有哪些技术细节？

### 配置分层

`config.yaml` 保存非敏感运行参数和功能开关，`dev/prod` profile 分别指向 `.env.dev` 和 `.env`；密钥、数据库连接串等敏感值放在 dotenv 文件或系统环境变量中。实际优先级是：

```text
显式进程环境变量 > config.yaml 当前 profile > profile 对应的 .env
```

生产默认选择 `prod`，本地脚本只临时设置 `FITNESS_PROFILE=dev`。这样 systemd 仍可直接执行 Gunicorn，不依赖 PowerShell 启动脚本。

### 进程与连接池

生产链路是 `systemd → Gunicorn(4) → UvicornWorker → FastAPI`。SQLAlchemy 连接池参数按 worker 计算：`pool_size=5`、`max_overflow=10`，所以理论峰值可能达到 `4 × (5 + 10) = 60` 个数据库连接，而不是全服务 15 个。

连接池启用 `pool_pre_ping` 发现失效连接，`pool_recycle=3600` 回收长寿命连接，`pool_timeout=30` 限制等待时间。面试时可以进一步说明：worker 数、LLM 并发和数据库最大连接数必须联合容量规划，不能分别拍脑袋配置。

### 为什么用 Gunicorn 多进程？

多进程提供故障隔离并利用多核，也能让一个阻塞请求不拖住整个服务。但进程内缓存、Semaphore、队列深度和 RAG 实例都不会自动跨 worker 共享；这正是未来引入 Redis、独立任务队列或共享推理网关时要解决的问题。

## Q30：测试和评估体系如何覆盖一个非确定性的 Agent 系统？

### 分层验证

1. **确定性单元测试**：路由规则、记忆组装、身份绑定、食物口径换算、模型代理与 RAG 组件；外部模型使用 mock，当前可重复基线为 185 项。
2. **数据库约束与迁移验证**：在迁移前检查重复数据，遇到不明确冲突就停止；迁移后验证唯一约束、检查约束和种子数据。
3. **接口契约测试**：验证 SSE 事件顺序、`[DONE]`、错误终止、历史消息归属以及 `request_id/session_id` 行为。
4. **真实模型评估**：使用独立数据集检查检索相关性、忠实度和回答相关性，不把会波动且收费的在线调用混入稳定单测。
5. **生产验收**：结合 `request_id` 查看 systemd 日志中的上下文加载、路由、排队、provider 首块、首正文和总耗时。

### 为什么不能只看“测试都通过”？

单元测试能证明确定性代码没有回归，但不能证明模型输出在真实问题上足够好。反过来，几条人工体验正常也不能证明并发写入、越权和异常恢复可靠。因此 Agent 系统需要同时维护代码测试、离线评测集、链路指标和人工安全审查。

### 当前评估边界

目前真实 RAG 数据集只有 15 个案例，旧的 5 案例报告是在不同模型和索引条件下生成的，不能拿来直接做升级前后结论。下一步应固定模型、Prompt、知识库快照和评测集版本，再做可复现实验，并补充路由混淆矩阵、工具成功率、TTFT P50/P95、重复写入率和失败恢复率。

- 实现 Chroma + BM25 + 加权 RRF 的混合检索链路，完成 embedding 从 1024 维到 2048 维的索引迁移，并将索引构建从 Gunicorn 多 worker 启动阶段拆为独立部署任务。
- 建立 185 项可重复 unittest 基线，并将确定性回归测试、真实模型评估和生产请求分段观测分开，提升 Agent 系统的可定位性和发布可信度。

## 面试表达注意事项

### 可以明确说已实现

- 结构化混合路由和会话承接；
- 稳定 `session_id`、`request_id`；
- 工作、情景、语义三层记忆；
- 服务端绑定工具用户身份；
- 模型与工具链真实流式输出；
- 小程序历史消息串流修复；
- 食物缓存口径和状态重构；
- 请求阶段耗时和首 Token 日志；
- 独立生产迁移与部署脚本；
- `embedding-3` 2048 维索引及 64 条批量限制。

### 只能说已有框架或待验证

- RAGAS 评测体系已经搭建，但数据规模较小；
- Query Expansion、HyDE、Self-RAG 和 Agentic RAG 在代码中可选，不是生产请求全部开启；
- Expert Review 存在于非流式完整图，线上主要流式路径会跳过；
- 三层记忆已经落地，但情景摘要和长期记忆治理仍是首版。

### 不能说已经完成

- 器械拍照识别；
- 自动生成并持续调整训练计划；
- 完整的自主规划—反思—恢复循环；
- LangSmith 或完整分布式 Trace；
- Prometheus 监控和告警；
- 经过大规模真实用户验证的效果指标；
- “RAG 正确率 92%”或旧稿中的对比实验结果。
