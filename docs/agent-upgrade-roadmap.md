# 健身助手 Agent：升级、治理与实施路线图

更新日期：2026-09-08  
状态：阶段 0–2 核心链路已在本地落地；阶段 3+ 暂缓，生产迁移需单独执行  
适用范围：微信小程序“健身助手Agent”、FastAPI 后端、Agent 编排、记忆、RAG、数据与部署

本文以当前源码为准，合并了对产品形态、器械拍照识别、Agent 路由、三层记忆、首 Token 延迟、安全与工程基础的审计结果。旧说明文档仅作为历史背景，不作为当前实现依据。线上体验仍需结合实际部署版本、反向代理配置和生产日志复核。

### 当前实现边界

本轮按“阶段 0–2、复用现有链路、不另起 Agent 框架”的约束完成了首版改造：

- 继续使用 `LLMManager`、`graph.py`、`MemoryManager`、`ConversationLog` 和现有工具；
- `ConversationLog` 继续承担逐轮情景记忆，只新增 `ConversationSession` 保存工作状态和幂等游标，`UserMemory` 保存带来源/置信度/有效期的语义事实；
- 真实流式、请求时序、服务端身份绑定、结构化路由、稳定 `session_id`、上下文消息、重复请求回放、图片校验和每日记录并发创建已接入；
- 阶段 3 的器械照片识别、阶段 4+ 的计划服务化、主动提醒和复杂主教练循环仍未实现；
- 生产发布前执行 `scripts/migrate_phase02.py`。重复每日记录仍需人工处理；旧版食物缓存会备份后重建为 v2 表并导入常见食物参考数据，避免把混合口径数据带入新系统。

## 1. 核心结论

当前产品已经具备多角色提示词、工具调用、RAG、用户数据和对话持久化，但整体仍更接近“关键词路由后的固定工作流”，还不是能够稳定维护目标、理解上下文、选择行动、验证结果并持续调整的教练 Agent。

升级时应坚持以下决策：

1. 先修复安全、真实流式、路由和会话状态，再扩大器械识别及主动功能。
2. 用一个面向用户的“主教练”协调能力，不让用户感知三个割裂且只能三选一的 Agent。
3. 简单、确定的记录和查询继续走规则与业务服务；模糊、多领域任务才使用模型决策。
4. 建立工作记忆、情景记忆、语义记忆三层结构；饮食、运动、计划等业务表仍是事实来源。
5. 模型不能自行决定用户身份，不能把“建议”当作“已执行”，所有写操作都要校验、幂等并回读确认。
6. 器械照片识别必须采用“识别证据 → 目录匹配 → 用户确认/补拍 → 可信教学”的闭环，不能只让视觉模型自由生成答案。

## 2. 当前系统与已确认问题

### 2.1 当前请求链路

```text
小程序发送消息
  → FastAPI 鉴权并查询用户和今日状态
  → stream_user_message 关键词路由
  → MemoryManager 加载画像、日/周统计和历史对话
  → 将记忆拼入 System Prompt
  → chat / nutrition / fitness Agent
  → 可选工具或 RAG
  → SSE 返回并在完成后保存一轮问答
```

主要代码位置：

- `backend/app/agents/router.py`：关键词和可选 LLM 路由。
- `backend/app/agents/graph.py`：完整图、独立流式入口、记忆装配和对话保存。
- `backend/app/memory/`：画像、统计、历史和摘要。
- `backend/app/agents/*_agent.py`：专业提示词、工具循环与流式实现。
- `backend/app/models.py`：用户、日志和对话表。
- `backend/app/main.py`：API、SSE、业务接口和部分后台任务。

### 2.2 路由问题

本节 2.2–2.6 保留的是阶段 0–2 改造前的审计记录，用于说明改造依据；当前完成状态
以文档第 11 节清单和源码为准。

改造前线上小程序主要使用流式入口，而流式入口调用：

```python
hybrid_route(user_message_clean, require_llm_confirm=False)
```

因此改造前实际在线链路对无关键词和模糊输入不会做语义确认，而是直接进入 `chat`。
当前流式路径统一使用 `require_llm_confirm=True`，并传入会话上下文；非流式图和流式
路径共用同一套结构化路由入口。

当前关键词评分存在以下结构性问题：

- `记录一下`、`帮我记`被放在营养词表中，会把运动记录拉向营养师。
- `多少`是营养关键词，会误判“你今年多少岁”等普通问题。
- `增肌`、`减脂`同时属于营养和健身，平分时固定优先营养。
- 只识别领域，不识别用户意图是查询、记录、修改计划、器械识别还是安全风险。
- 没有使用上一轮 Agent、待补参数或当前计划，无法理解“第二个呢”“换成哑铃”。
- 同一输入即使同时包含饮食和运动，也只能三选一，另一项任务可能被丢弃。
- 代码保留了 `mixed` 分支，但当前 `_keyword_match()` 不会返回 `mixed`，属于不可达逻辑。
- 词表采用简单子串计数，重复短语、长短词重叠和单字身体部位都会造成权重失真。
- 失败统一回退到 `chat`，没有“需要澄清”“多领域协调”“安全转介”等状态。

当前规则的可复现反例：

| 用户输入 | 当前关键词结果 | 目标行为 |
| --- | --- | --- |
| 记录一下跑步30分钟 | nutrition | `record_exercise` 快速路径 |
| 帮我记一下卧推5组 | nutrition | fitness，并补齐或确认参数 |
| 跑步消耗多少卡路里 | nutrition | fitness 的运动热量查询 |
| 增肌期间训练和饮食怎么安排 | nutrition | 主教练协调 fitness + nutrition |
| 第二个呢 | chat | 继承当前会话候选列表 |
| 换成哑铃 | chat | 结合当前计划进入 `modify_plan` |
| 你今年多少岁 | nutrition | 普通聊天 |
| 我想减肥但膝盖疼 | 流式入口进入 chat | 安全优先，健身建议并提示必要转介 |
| 吃了苹果，顺便跑了5公里 | nutrition | 拆分两个记录动作并分别确认 |

### 2.3 记忆与上下文问题

当前系统不是完整的多层记忆，而是“用户字段 + 业务统计 + 原始问答日志 + Prompt 拼接”：

- API 不接收稳定 `session_id`，流式保存固定传 `None`，每一轮问答几乎成为独立会话。
- Agent 的 `messages` 只有本轮用户消息，无法保留规范的多轮角色结构。
- 最近历史被转换成文本并放入 System Prompt，可能把历史用户输入提升为系统级指令，形成持久化提示词注入。
- AI 的旧错误回复会作为“记忆”再次注入，产生自我强化。
- 7 天历史和 1 天历史重复查询，其中一份在增强 Prompt 路径中没有实际消费。
- `ConversationSummarizer` 在生产中几乎不会触发；即使触发，摘要结果也没有持久化或真正替换上下文。
- `extract_key_info()` 只做少量关键词识别，不能可靠提取伤病、偏好、计划、纠正和约束。
- `load_all_memory()` 与 `UserProfileLoader` 手工维护两套画像结构，部分目标、训练偏好、饮食偏好和热量调整可能丢失。
- 没有来源、置信度、用户确认、有效期、冲突替换和细粒度删除机制。
- 历史只按时间截取，没有相关性、领域、重要度与新鲜度排序。
- 用户消息只在完整回复结束后与回答一起保存；中途失败会丢失本轮，错误回答却可能被保存并参与后续上下文。
- 工具调用、图片、模型版本、耗时、执行状态和用户纠正没有进入统一消息或事件模型。

### 2.4 首 Token 与并发问题

已确认的主要延迟来自后端编排：

- 改造前 `nutrition_agent.py` 和 `fitness_agent.py` 在输出正文前先执行一次完整、非流式的 `bind_tools(...).invoke(...)`；当前 `stream=True` 路径已改为流式工具决策，并增量合并工具参数。
- 工具场景仍需等工具参数完整后才能执行工具，但工具后的最终回答使用 `.stream()` 逐块发送；确定性记录路径直接返回业务结果，不伪造模型 token。
- 改造前 `chat_agent` 虽然流式生成，但 `graph.py::chat_stream()` 会先收集完整文本以解析意图标记；当前已改为只缓存可能的标记前缀，正文直接流出。
- 改造前 SSE 状态事件在画像、统计和历史加载之后才发送；当前会先发送接收状态，再执行上下文装配。
- `LLMManager._LLMProxy.stream()` 在迭代真正开始前释放信号量，生成阶段未受限。
- `bind_tools()` 返回底层对象，专业 Agent 绕过并发限制与排队通知。
- 排队回调是全局可变状态，并发请求可能覆盖彼此。
- 当前缺少请求级时序日志，无法在生产中区分数据库、路由、模型排队、模型首块、应用首块和 Nginx 缓冲。

当前配置已经关闭 GLM Thinking，因此“思考模式”不是主要原因。后续可让高速模型承担模糊路由和工具选择，能力模型负责最终回答，但必须先修复应用自身的假流式和多轮调用。

### 2.5 安全、数据与运行问题

发布新功能前需要处理：

- localhost 无 Token 时默认使用用户 1；若反向代理后的客户端地址仍是 `127.0.0.1`，可能形成生产认证绕过。
- Agent 工具把 `user_id` 暴露给模型并直接执行模型参数，存在跨用户读写风险。用户身份必须由服务端运行上下文绑定。
- 聊天输入没有合理长度限制；日志会记录部分用户原文，工具还会记录参数和结果，需要脱敏与保留策略。
- 上传接口读取完整文件并主要依赖扩展名，缺少大小、MIME、真实解码、像素和图片元数据校验。
- IP 限流在反向代理下可能把所有用户视为同一来源，或被不可信转发头影响；模型调用还需要用户级额度。
- `daily_logs` 缺少 `(user_id, date)` 唯一约束；记录工具没有幂等键，重试可能重复写入。
- 日志主表与明细存在分段提交，失败后可能留下不完整状态。
- 食物热量缓存 v3 已区分每 100g、每 100ml 和每 1 单位，液体支持 `1g = 1ml`；旧缓存迁移时归档并重建，再幂等导入版本化的常见食物参考数据。
- 未知食物热量仍使用进程内 daemon 线程回填，但已持久化 `pending/ready/failed` 状态，异常和超时会进入失败终态；后续仍应改为持久任务队列以支持进程重启后自动续跑。
- 没有正式迁移框架；`create_all()` 不能升级已有生产表。
- `main.py` 聚合了接口、业务、模型估算和后台线程，继续增加功能会放大维护风险。

### 2.6 RAG、测试与部署问题

- 默认知识目录是 `./knowledge_base`，仓库实际目录为 `knowledgebase/`；部署未显式配置时可能只建立默认文档。
- 健身和营养使用不同 RAG 初始化方式，营养首次检索可能额外冷启动一套实例。
- 当前工具使用普通 `search()`，部分 Agentic RAG 配置没有实际收益。
- 改造前本地全量测试曾观察到 104 项、17 个 error；记忆模块单独运行 34 项、4 个 error。本轮已建立可重复的 unittest 基线，当前全量 167 项通过；外部模型不可用时仍可能打印降级日志。
- 本地 `main` 与 `deploy` 的运行时代码基本一致，依赖文件存在差异；线上从 `deploy` 发布，必须记录构建提交和锁定依赖。
- 小程序历史消息串流修复目前是本地修改，未提交和部署前线上不会生效。
- 后端设置了 `X-Accel-Buffering: no`，但仓库无法证明生产 Nginx 已关闭缓冲，需要线上验证。

## 3. 目标 Agent 架构

建议对用户只呈现一个“健身主教练”，内部按能力和工具调度：

```text
文本 / 图片 / 卡片操作
        ↓
认证 RequestContext（后端绑定 user_id、session_id、request_id）
        ↓
高精度快速意图规则
        ├─ 明确记录、查询、卡片操作 → 直接调用业务服务
        └─ 省略句、模糊或多领域请求
                    ↓
会话上下文 + 结构化语义路由
                    ↓
主教练 Orchestrator
        ├─ 营养能力与工具
        ├─ 健身能力与工具
        ├─ 器械视觉识别与目录
        ├─ 计划和训练执行工具
        └─ 安全边界与澄清
                    ↓
验证工具结果与最终数据库状态
                    ↓
流式答复 + 异步记忆整理
```

固定流程继续用于登录、精确查询、记账、删除和确定性计算。Agent 循环只用于需要规划、选择工具、根据结果调整或等待用户确认的任务。

## 4. 路由系统改造

### 4.1 从“选择角色”改为“识别任务”

新的路由输出不只返回一个 Agent 名称，而应返回结构化决策：

```json
{
  "mode": "fast_action | single_domain | multi_domain | clarify | safety",
  "primary_domain": "fitness | nutrition | general | equipment",
  "domains": ["fitness", "nutrition"],
  "intent": "record | query | advise | create_plan | modify_plan | identify_equipment",
  "entities": {},
  "needs_tools": true,
  "missing_fields": [],
  "confidence": 0.92,
  "reason_code": "EXPLICIT_EXERCISE_RECORD"
}
```

`reason_code` 用于观测和评估，不使用自由文本理由驱动业务逻辑。服务端必须校验枚举、字段和置信度。

### 4.2 四级决策顺序

#### 第一级：高精度确定性规则

只处理不会产生歧义的输入：

- 卡片按钮、表单和图片上传等结构化事件。
- 明确的饮食记录和运动记录，并提取业务参数。
- 精确删除、确认、取消、撤销。
- 已知 ID 的计划开始、完成、替换。

规则应基于“动作 + 实体 + 必要参数”，不能继续按平铺关键词累计分数。通用词如“多少”“记录一下”“增肌”不能单独决定领域。

#### 第二级：会话承接

对于“第二个”“继续”“换成哑铃”“就按这个来”等短输入，优先读取第一层工作记忆：

- 上一轮路由和 Agent；
- 当前候选列表；
- 等待确认的动作；
- 缺失参数；
- 活跃计划及版本。

如果没有可承接状态，再进入澄清或语义路由，不能直接回退闲聊。

#### 第三级：结构化语义路由

只有模糊、跨领域或规则未覆盖的输入才调用高速模型。输入包括当前消息、最近少量会话和活跃任务摘要，输出严格 JSON，并设置低输出上限与超时。

高置信度单领域请求进入对应能力；多领域请求交给主教练拆分；低置信度请求只问一个最有信息量的澄清问题。

#### 第四级：执行中动态重路由

路由不是请求开始时的一次性决定。工具返回器械不匹配、计划冲突、数据缺失或安全信号后，主教练可以：

- 补充查询；
- 切换能力；
- 请求用户确认；
- 降级为通用建议；
- 停止执行并说明原因。

每次任务设置最大步骤、最大模型调用、总超时和成本预算，避免无限循环。

### 4.3 多意图和跨领域处理

不再强制把所有请求压成 nutrition、fitness、chat 三选一：

- “训练后吃什么”以营养建议为主，但读取本次训练事实。
- “增肌期间训练和饮食怎么安排”由主教练分别生成训练和饮食子任务，再合并为一致计划。
- “吃了苹果又跑了5公里”拆成两个独立写操作，分别校验并返回各自结果。
- 涉及疼痛、眩晕或急性不适时先进入安全策略，不让普通关键词竞争覆盖风险信号。

### 4.4 路由失败策略

- 规则冲突：进入语义路由，不采用固定的营养优先。
- 模型超时：根据当前会话和高精度规则给出有限降级；无法判断时澄清。
- 多领域但无法协调：明确拆成两部分，不静默丢弃其中一个。
- 未知能力：由主教练回答能力边界，不伪造工具或执行结果。
- 路由结果与工具参数分离，路由器不得产生任意 `user_id`。

### 4.5 路由评估

建立独立数据集，至少覆盖：

- 明确单领域；
- 通用词干扰；
- 多意图；
- 跨领域；
- 上下文省略；
- 计划修改；
- 器械识别；
- 健康安全；
- 对抗性和目录外输入；
- 模型超时与格式错误。

重点指标：

| 指标 | 说明 |
| --- | --- |
| Intent accuracy / Macro F1 | 防止大量简单样本掩盖少数关键意图 |
| 高风险漏判率 | 疼痛、过敏、越权写入等不得被普通路由覆盖 |
| 多意图完整率 | 一个请求中的多个动作都被识别和处理 |
| 澄清有效率 | 低置信度时是否提出能推进任务的问题 |
| 路由耗时 P50/P95 | 规则路径和模型路径分别统计 |
| 降级正确率 | 模型不可用时不误写数据、不伪造完成 |

记录 `route_version`、规则命中、模型决策、置信度、最终工具轨迹和用户纠正，支持离线回放。日志不保存不必要的敏感原文。

## 5. 三层记忆架构

### 5.1 第一层：工作记忆

职责是维护当前会话和正在执行的任务：

- 稳定的 `session_id`；
- 最近 8–12 条规范角色消息；
- 当前路由、候选项和待补参数；
- 工具调用及结果；
- 活跃计划版本；
- 当前上传图片和识别任务；
- 等待确认、可撤销动作和失败状态。

建议新增：

- `conversation_sessions`
- `conversation_messages`

消息角色保留为 `user / assistant / tool / system`。达到 Token 预算或会话结束后异步压缩，不把原始用户内容拼成 System Prompt。

### 5.2 第二层：情景记忆

职责是记录“发生过什么”：

- 完成或跳过的训练；
- 某次器械识别及用户确认；
- 用户对动作、计划和建议的反馈；
- 某个阶段计划及调整原因；
- 一段时间内的饮食或训练模式。

建议实体：

```text
MemoryEpisode
- user_id
- scope: shared / fitness / nutrition / equipment
- episode_type
- summary
- structured_data
- source_message_ids
- occurred_at
- importance
- confidence
- expires_at
- embedding（按数据规模后续增加）
```

读取时结合相关性、时间、重要度和有效期选择少量记录。摘要和提取在本轮流式完成后异步运行，不能阻塞首 Token。

### 5.3 第三层：语义记忆

职责是维护稳定、可复用且可纠正的事实：

- 身体数据和当前目标；
- 过敏、伤病和安全限制；
- 饮食、训练、时间与器械偏好；
- 已确认的训练水平；
- 长期可用器械；
- 当前有效计划和长期约束。

建议实体：

```text
UserMemory
- user_id
- namespace
- key
- value_json
- source: user_input / tool / conversation
- confidence
- verified_by_user
- status: candidate / active / superseded
- valid_from / valid_until
- source_message_id
- updated_at
```

用户表和业务工具写入的事实优先级最高；模型推断只能进入 `candidate`。伤病、过敏等高风险信息需确认。新目标生效时旧目标标记为 `superseded`。

### 5.4 业务事实不等于记忆

`DailyLog`、`FoodItem`、`ExerciseItem`、训练计划和执行记录继续作为业务事实来源。记忆层只保存面向 Agent 的摘要、偏好和情景，不复制或篡改事实。

推荐上下文包：

```text
静态 System Prompt
+ 必须注入的语义事实（目标、过敏、伤病）
+ 实时业务状态（今日摄入、近期训练、活跃计划）
+ 与本次问题相关的 3–5 条情景记忆
+ 当前会话最近消息
+ 本轮消息
```

由统一 `MemoryContextBuilder` 按 Agent、任务和 Token 预算组装，禁止各 Agent 自己重复查询和格式化历史。

### 5.5 记忆写入与治理

1. 收到消息后先保存用户消息和请求状态。
2. 加载工作记忆，完成路由和响应。
3. 保存 assistant/tool 消息及完成、失败或取消状态。
4. 响应结束后异步生成情景摘要和语义记忆候选。
5. 按来源、类型和主键去重，处理冲突与过期。
6. 向用户提供“Agent 记住了什么”“修改”“忘记这条”和清空入口。

不得从 assistant 自己的回答中直接生成已确认事实。任何删除必须同步处理派生摘要和检索索引。

## 6. 产品能力升级

### 6.1 拍照识器械

该功能解决用户在器械前“不认识、不会调、练哪里”的高价值即时问题，也是视觉 Agent 的自然入口。

用户流程：

1. 拍照或从图库选择，提示拍全器械和铭牌。
2. 检测是否存在可识别目标；多器械时让用户裁剪或选择。
3. 视觉模型输出候选、可见文字、关键证据和缺失信息。
4. 与受控器械目录和动作映射匹配。
5. 高置信度时展示结果；有歧义时给候选或要求补拍。
6. 从审核后的动作库和厂商资料生成教学卡片。
7. 用户可追问、纠错、加入计划或开始训练。

结果卡片至少包含：

| 字段 | 要求 |
| --- | --- |
| 器械名称 | 常用名和别名；品牌型号无证据不猜 |
| 识别状态 | 已匹配、待确认、需补拍、目录外 |
| 支持动作 | 多功能器械先让用户确认动作 |
| 训练部位 | 主要和辅助肌群按动作区分 |
| 使用方法 | 调节、起始位、动作、结束归位 |
| 安全提示 | 常见错误及需查看铭牌的型号差异 |
| 教学来源 | 审核内容或可追溯来源 |
| 操作 | 追问、重拍、纠错、加入训练 |

首版建议覆盖 20–30 类常见器械，以真实场馆照片验证不同品牌、角度、遮挡和多器械背景。数量是范围建议，不是准确率承诺。

视觉识别结果应作为工具数据处理，图片文字不能改变系统指令。图片限制大小、像素和格式，真实解码后再处理，移除不必要元数据，并采用最短必要保存期限。

### 6.2 服务端可执行计划

把当前主要存在小程序本地的训练计划迁移到服务端：

- 目标、周期、日期、时长和器械约束；
- 计划动作、组次、重量、休息和替代项；
- 版本、草稿、已确认、进行中和完成状态；
- 本地计划导入、预览、去重和冲突处理。

计划与实际执行分开保存。跳过、缩短或取消不能被记录为完整完成。

### 6.3 动态调整和反馈闭环

支持：

- “今天只有15分钟”
- “这个器械有人用”
- “把今天移到周五”
- “换成哑铃”
- “这个动作膝盖不舒服”

系统读取当前计划、完成情况、工作记忆和长期约束，给出变更草稿。低风险且用户明确指定的操作可执行并提供撤销；较大调整先展示差异。写入后重新查询版本，确认训练页读取到相同结果。

训练后收集实际组次、重量、主观难度和未完成原因。周复盘必须区分计划、已记录事实和缺失信息，不能把未记录推断为未训练。

### 6.4 主动跟进

先实现应用内“教练待办”：

- 待确认计划；
- 待补充训练反馈；
- 待查看周复盘；
- 因缺少信息暂停的 Agent 任务。

再按微信能力和用户授权评估订阅消息。设置频率、静默时段、取消方式和重复事件去重。后台调度应使用持久化任务，不依赖小程序前台或进程内 daemon 线程。

## 7. 技术架构改造

### 7.1 统一任务执行服务

流式和非流式入口共享同一个执行核心，区别仅在事件传输：

- `status`：真实执行阶段；
- `token`：正文片段；
- `tool_start / tool_result`：经过脱敏的工具状态；
- `clarification`：等待用户补充；
- `action_preview`：待确认写操作；
- `action_committed`：已写入并回读验证；
- `error`：可恢复或终止错误；
- `done`：最终状态。

移除为了在文本尾部解析意图而缓存完整回答的设计。意图由路由层结构化生成，正文可以直接流式发送。

### 7.2 模型调用治理

- 修复信号量，使许可覆盖流迭代完整生命周期。
- `bind_tools()` 后仍通过统一代理、限流、超时和观测。
- 排队状态按请求保存，不使用全局可变回调。
- 路由/工具选择与最终回答可以使用不同模型配置。
- 支持模型级和用户级并发、配额、超时和熔断。
- 工具流式调用已接入：工具参数仍需完整后执行，但模型决策和最终回答不再使用阻塞式首轮 `invoke()`。
- 每个 Agent 任务设置最大步骤、最大工具调用、Token 和成本预算。

智谱官方提供流式工具调用，可在兼容性验证后用于降低工具决策等待：[工具流式输出](https://docs.bigmodel.cn/cn/guide/capabilities/stream-tool)。高速模型选型以真实路由集和工具调用集 A/B 结果为准：[模型概览](https://docs.bigmodel.cn/cn/guide/start/model-overview)。

### 7.3 首 Token 观测

每个请求记录同一 `request_id` 下的时间点：

```text
request_received
auth_completed
user_context_loaded
route_completed
first_sse_status
memory_context_ready
llm_request_started
provider_first_chunk
application_first_token
response_completed
```

分别统计“首个状态”和“首个正文 Token”。若普通聊天仍整段到达，检查应用缓存和生产 Nginx `proxy_buffering`，不能只依赖响应头推断。

### 7.4 数据模型

建议按阶段增加：

| 实体 | 职责 |
| --- | --- |
| ConversationSession / Message | 会话、规范消息、工具事件和状态 |
| MemoryEpisode / UserMemory | 第二层情景记忆和第三层语义记忆 |
| Equipment / EquipmentExercise | 器械目录、别名和动作映射 |
| RecognitionTask / Candidate | 图片任务、候选、证据和用户确认 |
| UserGoal | 目标、有效期和状态 |
| TrainingPlan / PlanItem | 计划及版本 |
| TrainingSession / SessionItem | 实际训练和反馈 |
| AgentTask / ToolExecution | 任务进度、重试和幂等 |

引入正式迁移工具并先补约束、索引和外键策略。业务写入在同一事务内完成；所有可重试操作携带幂等键；计划更新使用版本号避免覆盖并发修改。

LangGraph checkpointer 可保存执行进度和暂停恢复，store 可辅助长期记忆，但都不能替代业务数据库的事务和授权。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### 7.5 安全与隐私

发布门槛：

- 删除或严格限制 localhost 免认证逻辑。
- `RequestContext` 服务端绑定用户身份，工具 schema 不暴露任意用户 ID。
- 参数使用 Pydantic/JSON Schema 校验，写工具限制资源所有权。
- 聊天、上传和模型调用设置大小、类型、频率和成本限制。
- 日志采用结构化字段并脱敏，不记录图片、完整提示词和不必要的健康信息。
- 记忆有来源、确认、有效期、查看、修改和删除能力。
- 图片和识别任务按用户隔离，定义第三方模型处理和保存策略。
- 健康建议设置安全边界，不做诊断或康复处方。

## 8. 工程与质量基础

### 8.1 代码治理

- 将 `main.py` 拆分为 API 路由、应用服务、领域服务和基础设施。
- 将路由、记忆组装、工具执行和 SSE 协议做成独立可测试模块。
- 统一 RAG 单例、目录配置、索引版本和启动健康检查。
- 统一营养与健身工具循环，避免两套相似但行为不同的实现。
- 锁定依赖并记录部署提交、迁移版本、模型配置和 RAG 索引版本。
- 先确认并保护当前工作区中尚未提交的小程序修复和文档。

### 8.2 测试体系

在新增功能前恢复现有测试基线，并增加：

- 路由反例和多轮上下文测试；
- 流式首块测试，防止再次整段缓存；
- 并发信号量和跨请求回调隔离测试；
- 会话、三层记忆、冲突、过期和删除测试；
- 工具授权、幂等、事务和版本冲突测试；
- RAG 索引内容及目录外查询测试；
- 器械识别离线集和危险教学阻断集；
- 计划修改和数据库最终状态端到端测试；
- 生产相同迁移路径的临时数据库测试。

模型行为评估应同时检查轨迹和最终环境状态；“回复说已完成”不等于数据库真的完成。[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 9. 分阶段实施路线

| 阶段 | 交付内容 | 完成门槛 |
| --- | --- | --- |
| 0：稳定与安全 | 真实流式、耗时埋点、并发治理、身份绑定、输入上传校验、测试数据库、迁移框架 | 普通聊天能逐块输出；无跨用户工具参数；关键测试绿色 |
| 1：路由与工作记忆 | 新 RouteDecision、确定性快速路径、上下文承接、session/message 表、多意图测试 | 典型反例通过；流式/非流式路由一致；短句能承接当前任务 |
| 2：三层记忆 | MemoryContextBuilder、情景摘要、语义候选、冲突过期、查看和忘记 | 记忆可追溯和纠错；无原始历史 System Prompt 注入；读取受 Token 预算控制 |
| 3：器械识别验证 | 器械目录、真实照片集、视觉模型对比、教学来源和安全评估 | 明确支持范围、失败模式、成本和延迟，危险错误作为阻断项 |
| 4：器械识别首版 | 拍照、补拍、候选确认、教学卡片、追问和纠错 | 真机灰度、目录外降级、图片隔离和保留策略通过 |
| 5：计划服务端化 | 计划 API、版本、导入、识别后加入计划、训练执行记录 | 计划与事实分离；重试不重复；新旧客户端兼容 |
| 6：Agent 调整闭环 | 主教练工具循环、改期/替换、反馈、暂停恢复和回读验证 | 多轮任务、异常恢复和最终数据库状态通过 |
| 7：长期服务 | 周复盘、教练待办、经授权的主动提醒 | 复盘有事实依据；记忆可删除；通知可关闭且不重复 |

阶段 0 和器械目录/照片数据准备可以并行；器械功能进入用户灰度前必须完成阶段 0 的身份、上传和观测要求。

## 10. 验收指标

### 10.1 路由与任务

- 明确记录意图正确率和多意图完整率。
- 上下文承接成功率。
- 安全场景漏判率。
- 工具调用成功率、重复写入率和最终状态一致率。
- 澄清后任务完成率，而不是只统计首次分类。

### 10.2 记忆

- 用户事实准确率与错误记忆率。
- 冲突更新、过期和删除传播正确率。
- 跨 Agent 共享必要信息的成功率。
- 跨用户隔离为零泄露。
- 上下文 Token、记忆读取 P50/P95 和异步整理成本。

### 10.3 性能

- 首个 SSE 状态 P50/P95。
- 首个正文 Token P50/P95。
- 工具开始、工具完成和总任务耗时。
- 路由规则路径与模型路径分别统计。
- 模型排队、超时、降级和 Nginx 缓冲异常比例。

初始工程目标可以设为：普通请求首个状态尽量小于 200ms，普通聊天正文首 Token 的 P50 小于 1.5s；工具任务应立即展示真实进度。最终阈值以生产基线、地域网络和模型服务实测确定，不作为未经验证的产品承诺。

### 10.4 器械识别

- 器械类别正确率和目录外识别能力。
- 多器械、遮挡、不同品牌和角度表现。
- 错误但未提示不确定性的比例。
- 补拍后的解决率。
- 器械—动作—肌群—教学内容一致率。
- 查看教学后开始训练或加入计划的比例。

## 12. 暂缓与非目标

现阶段暂缓：

- 大量增加 Agent 角色；
- 让所有请求都经过 LLM 路由；
- 继续堆叠高级 RAG 而不验证索引内容；
- 把 checkpoint 当成业务数据库；
- 根据模型自报置信度直接接受器械识别；
- 静态照片动作纠错扩展成康复或医疗诊断；
- 在基础安全、流式和测试未稳定前上线自动写计划和主动推送。

优先验证用户是否因为器械识别、可执行计划和持续调整获得真实价值，再扩展语音、饮食拍照、设备数据和视频动作分析。
